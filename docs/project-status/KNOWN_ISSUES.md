# Problemas conocidos

Registrados durante FASE 0 (no bloqueantes para cerrar la fase):

1. **Python 3.14.4 es la única versión instalada localmente**, mientras que `.github/workflows/tests.yml` usa Python 3.12 en CI. No se detectó ningún bloqueo real: se verificó (vía `pip download`, sin instalar) que Django 5.2.17, psycopg 3.3.4 (incluida la rueda binaria `psycopg_binary-3.3.4-cp314-cp314-win_amd64.whl`), djangorestframework 3.18.0, python-dotenv y gunicorn tienen paquetes compatibles con Python 3.14 en Windows. Aun así, dado que Python 3.14 es muy reciente, conviene tenerlo presente si aparece algún comportamiento inesperado al crear el entorno virtual en FASE 1; alinear la versión local con la de CI (o viceversa) es una decisión pendiente del usuario, no un error actual.
2. **pgAdmin 4 no fue abierto ni verificado visualmente por Claude** (es una aplicación gráfica). El binario existe en `C:\Program Files\PostgreSQL\18\pgAdmin 4\runtime\pgAdmin4.exe` y hay perfiles de configuración previos en `%APPDATA%\pgAdmin` y `%APPDATA%\pgadmin4`, lo que sugiere que ya se ha usado antes. Queda pendiente que el usuario lo abra y confirme que inicia correctamente, según `docs/setup/windows-postgresql-pgadmin-step-by-step.md`.
3. **No se probó una conexión autenticada real a PostgreSQL** (usuario/contraseña del superusuario `postgres`) porque `pg_hba.conf` exige `scram-sha-256` (correcto y seguro) y esa contraseña solo la tiene el usuario. Esto es esperado para FASE 0; se resolverá en FASE 2 siguiendo el runbook de PostgreSQL/pgAdmin.
4. **`psql` no estaba en el PATH del sistema**; se corrigió agregando `C:\Program Files\PostgreSQL\18\bin` al PATH de usuario (no al PATH de sistema, y sin usar `setx` para evitar el riesgo de truncado). Las terminales abiertas antes de este cambio no lo verán hasta reiniciarse.

Registrados durante FASE 1 (no bloqueantes para cerrar la fase):

5. **`python manage.py runserver` y `python manage.py test` no funcionan todavía con la configuración oficial (PostgreSQL)** porque el usuario de aplicación `erp_saas_app` y la base `erp_saas_dev` aún no existen — eso es exactamente el objetivo de FASE 2. `manage.py check` sí pasa (no requiere conexión), y `manage.py test` pasa usando `SimpleTestCase` (la vista `home` no toca la base de datos). El arranque HTTP completo del proyecto se verificó una sola vez con una base de datos SQLite temporal y explícita (permitido por CLAUDE.md únicamente como herramienta de prueba puntual), confirmando HTTP 200 y el contenido esperado en español; el archivo SQLite temporal se eliminó después de la prueba y no quedó ningún rastro en el repositorio. Este problema se resolverá automáticamente al cerrar FASE 2.
6. **`DB_PASSWORD=change-me` en `.env`** (archivo local, no commiteado) es un placeholder intencional hasta que en FASE 2 se cree el usuario `erp_saas_app` real en PostgreSQL con una contraseña elegida por el usuario.
