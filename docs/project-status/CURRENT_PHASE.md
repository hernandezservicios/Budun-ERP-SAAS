## Resumen de FASE 8
Primer dominio de negocio real del proyecto: `apps/inventory` (Categorías, Productos, Movimientos de stock). `Category` y `Product` heredan `TenantScopedModel` (FASE 3): aislamiento automático por tenant. El stock NUNCA es un campo desnormalizado: se calcula siempre a partir del libro mayor append-only `StockMovement` (stock actual = `stock_after` del movimiento más reciente), lo que hace imposible por diseño que el stock mostrado contradiga el historial. Capa de servicios (`services.py`) como única vía para crear movimientos (entrada/salida/ajuste), con `transaction.atomic()` + `select_for_update()` para evitar condiciones de carrera, y rechazo explícito de operaciones inválidas (cantidad ≤ 0, salida que dejaría stock negativo, ajuste sin cambios). PostgreSQL con `UniqueConstraint` (SKU y código de barras únicos por tenant, barcode parcial para permitir vacíos), `CheckConstraint` (precios/stock nunca negativos, cantidad de movimiento siempre positiva, stock posterior nunca negativo) e índices compuestos. ### Ampliación de FASE 8: Inventario Serializado
Tras el cierre inicial de FASE 8, el usuario auditó la fase y ordenó incorporar inventario serializado (IMEI/número de serie) antes de darla por cerrada — requisito que no existía en ningún documento previo del proyecto (búsqueda explícita sin coincidencias, ver `KNOWN_ISSUES.md` #35). Se agregó `Product.inventory_tracking_type` (`QUANTITY`/`SERIALIZED`) y el modelo `InventoryUnit` (equivalente de `StockMovement` para productos serializados: cada unidad física es su propia fila, disponibilidad = conteo de unidades `EN_STOCK`, nunca un contador desnormalizado aparte). Constraints de PostgreSQL: serial/IMEI 1/IMEI 2 únicos por tenant (parciales, permiten vacíos), IMEI 1 ≠ IMEI 2, al menos un identificador por unidad. Máquina de estados (`ALLOWED_UNIT_TRANSITIONS`/`services.transition_unit_status`) para los 8 estados pedidos, que impide vender una unidad ya vendida/reservada/en reparación. Búsqueda unificada (`services.search_catalog`) por nombre/SKU/código de barras/serie/IMEI, ya preparada para que FASE 10/11/15 la reutilicen sin reimplementarla. `services.get_current_stock`/`list_products_with_stock` siguen siendo el único punto de verdad de stock para ambos tipos de producto a la vez (anotación `Case/When` combinando `StockMovement` e `InventoryUnit`, sin N+1). Un producto no puede cambiar de tipo de seguimiento si ya tiene historial. Ningún mensaje de error ni log expone el IMEI/serie completo. Especificaciones de FASE 10-15 actualizadas (documentación únicamente) con la interfaz que cada una debe consumir. 175/175 tests OK (129 de la fase base + 46 nuevos de inventario serializado, incluyendo constraints, máquina de estados, búsqueda, multi-tenant y seguridad). ### Ampliación de FASE 10: Payment + PaymentAllocation (cuentas por cobrar)
Tras el cierre inicial de FASE 10, el usuario ordenó explícitamente extender el motor de pagos para que "un Payment pueda aplicarse a una o varias facturas del mismo Customer" — el cierre original había omitido `PaymentAllocation` con permiso explícito del usuario ("cuando no sea necesario"), y esta ampliación revierte esa decisión con el mismo nivel de autoridad. `Payment.sale` (`ForeignKey` directo a una única venta) se eliminó; `Payment.customer` (nulo solo para venta de mostrador) lo reemplaza. `PaymentAllocation` es el nuevo ledger append-only (nunca editado in-place: una asignación equivocada se corrige con `reverse_allocation`, `status=REVERSED` + auditoría, mismo patrón inmutable que `Return`). El saldo pendiente de una factura (`get_sale_balance_due`) y el saldo sin aplicar de un pago (`get_unallocated_payment_amount`) se calculan siempre desde el ledger, nunca como campo desnormalizado — mismo principio que `get_current_stock` en `apps.inventory.services`. Validado con `select_for_update()` sobre ambas filas (`Payment` y `Sale`) antes de aplicar cualquier monto: nunca excede lo disponible del pago ni el saldo pendiente de la factura, nunca cruza tenants ni clientes distintos, `apply_payment_to_sales` es todo-o-nada para repartir un solo pago entre varias facturas. Cambio de comportamiento intencional y documentado: un reembolso ahora solo puede salir del saldo SIN APLICAR de un pago (antes derivaba `Sale.payment_status=REFUNDED` directamente al reembolsar un pago ya aplicado) — hay que `reverse_allocation` primero; dos tests de FASE 10 (`test_reembolso_total_deja_estado_refunded`/`test_reembolso_parcial_deja_estado_partially_refunded`) se actualizaron para reflejar el flujo correcto de dos pasos. `get_customer_credit_balance`/`get_customer_pending_sales` son agregaciones de solo lectura (saldo a favor del cliente, facturas pendientes) preparadas explícitamente para que FASE 11 (POS) pueda cobrar cuentas por cobrar reales — sin construir ningún ledger contable completo ni UI de "cuenta corriente" en esta fase. Concurrencia real (`TransactionTestCase` + hilos): dos asignaciones simultáneas del mismo pago que exceden lo disponible, y dos asignaciones simultáneas a la misma factura que exceden su saldo pendiente — exactamente una gana en ambos casos. Vistas/plantillas de la pestaña "Pagos" del detalle de venta actualizadas para listar `PaymentAllocation` (monto aplicado a *esa* venta, correcto incluso si el pago cubre otras facturas) en vez de `Payment` directamente. 18 tests nuevos en `apps.sales` (128/128 en el módulo) — 389/389 tests OK en total. Documentado en `docs/payments.md` (reescrito) y `docs/sales.md`.
